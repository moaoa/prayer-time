Prayer sound plays twice

Analysis of why adhan audio is heard twice when using Test adhan or when a scheduled prayer alarm fires, plus a concrete fix plan for the Rust audio layer.

1. Symptom

When the user clicks Test adhan (Settings or Home) or when a prayer time is reached, the spoken MP3 appears to play two times — either as an obvious echo/overlap, or as two nearly identical copies through the same speakers.

2. How playback works today

Audio is played only in the Rust backend via rodio. The Vue frontend never plays MP3 files itself.

Relevant files:

  • src-tauri/src/audio_output.rs — play_sound()
  • src-tauri/src/prayer_scheduler.rs — trigger_alarm(), play_prayer_sound()
  • src/composables/useMultiSpeaker.ts — toggles multi-speaker via Rust state

3. Root cause (primary): multi-speaker plays on virtual monitor devices

Most likely

Linux exposes duplicate output endpoints

When multi-speaker mode is enabled, play_sound() enumerates every CPAL output device and spawns one playback thread per device: 

// audio_output.rs — when multi_speaker && devices.len() >= 2
for device in devices {
    thread::spawn(|| play_sound_on_device(path, &device));
}

On Ubuntu with PipeWire/PulseAudio, the device list often includes both:

  • Built-in Audio Analog Stereo — the real speakers
  • Monitor of Built-in Audio Analog Stereo — a loopback of what is already playing on that sink

Playing the same MP3 on both routes the audio to the same physical speakers twice. The user hears a doubled/echoed adhan. With 3+ virtual sinks, it can sound even worse.

flowchart LR MP3["dhuhr.mp3"] --> Thread1["Thread: Built-in Analog"] MP3 --> Thread2["Thread: Monitor of Built-in"] Thread1 --> Speakers["Physical speakers"] Thread2 --> Loopback["Loopback re-enters mix"] Loopback --> Speakers

This matches the warning already present in Settings (Arabic UI): virtual outputs like Monitor of … may appear on Linux when multi-speaker is on.

4. Secondary causes to rule out

CauseLikelihoodWhy it is / isn't the bug
Frontend plays audio twice Unlikely handlePrayerAlarmEvent only sends a desktop notification. No Audio element or second invoke on alarm.
Scheduler fires alarm twice Unlikely fired: HashSet deduplicates per prayer per day. Mutex guards the check.
Two app instances running Possible Autostart (enable() on mount) + a manually launched copy = two schedulers, two sounds at alarm time. Does not explain double play on a single Test click unless both instances receive events (they don't for invoke).
Multi-speaker OFF but still doubled Check setting With multi-speaker off, only play_sound_default() runs once. If doubling persists, verify localStorage multiSpeakerEnabled and list devices in Settings.

5. How to confirm before fixing

  1. Open Settings → Available audio outputs and note device names.
  2. Check whether multi-speaker toggle is ON.
  3. If you see any name containing Monitor, Loopback, or Null, that confirms the primary cause.
  4. Turn multi-speaker OFF and click Test adhan again.
    • If doubling stops → root cause confirmed.
    • If doubling continues → check for two running app processes (pgrep -a libya-prayer).

6. Recommended fix

Fix A — Filter virtual/loopback devices (required)

In audio_output.rs, skip non-physical sinks when collecting devices for multi-speaker playback. 

fn is_physical_output(name: &str) -> bool {
    let n = name.to_ascii_lowercase();
    !n.contains("monitor")
        && !n.contains("loopback")
        && !n.contains("null")
        && !n.contains("dummy")
}

Apply in collect_output_devices() and optionally in list_output_device_names() so the Settings list matches what will actually be used.

After filtering, if zero devices remain → fall back to play_sound_default().

Fix B — Prefer default device when only one physical sink (nice-to-have)

If filtered list has exactly one physical device, use play_sound_on_device once. If multiple physical devices (e.g. speakers + HDMI), keep parallel playback — that is the intended multi-room behavior.

Fix C — Single-instance guard (optional, separate issue)

Prevent two app processes (autostart + manual launch) from both playing scheduled alarms. Tauri supports a single-instance plugin or a file lock on startup.

7. Implementation steps

  1. Edit src-tauri/src/audio_output.rs: add filter helper; use it in device enumeration.
  2. Add Rust unit tests for name filtering (Monitor of … rejected, normal names kept).
  3. Optionally update Settings hint to say virtual devices are automatically excluded.
  4. Rebuild: pnpm tauri build
  5. Reinstall the .deb and verify Test adhan plays exactly once with multi-speaker enabled.

8. Expected result after fix

With multi-speaker ON on Linux: one playback thread per physical output (e.g. laptop speakers + HDMI monitor), but no duplicate loopback through Monitor of … sinks.

With multi-speaker OFF: unchanged — single default output, one play (already correct).
