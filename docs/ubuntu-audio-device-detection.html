1. The Ubuntu audio stack

Sound does not go straight from the app to the speaker. On modern Ubuntu (22.04+ / 24.04), PipeWire sits in the middle and owns the friendly device list you see in GNOME Settings.

Apps
Prayer Times, Chrome, Spotify… They ask “what can I play on?” through libraries (cpal/rodio, PulseAudio API, or PipeWire tools like pw-dump / pw-play).
PipeWire
Session manager (WirePlumber) builds sinks: one real output target each — “Speaker + Headphones”, “soundcore R60i NC”, HDMI ports, etc. PulseAudio apps talk to pipewire-pulse (compatibility layer).
ALSA
Low-level Linux audio API. Exposes the PCI sound chip as many device strings (hw:, plughw:, dmix:…) — different ways in, not different speakers.
Kernel / HW
Driver for the chip (e.g. Intel sof-hda-dsp / sofhdadsp) plus Bluetooth (bluez). Physical routes: built-in speakers, 3.5 mm jack, HDMI, BT headset.

2. Why one chip becomes many names

ALSA lists plugin paths for the same card. PipeWire collapses those into a few logical sinks with human names.

ALSA (raw) — confusing

What cpal often returns on Linux

  • pipewire
  • default
  • hw:CARD=sofhdadsp,DEV=0
  • hw:CARD=sofhdadsp,DEV=3
  • plughw:… / dmix:… / sysdefault:…

Same Intel card, many access aliases + HDMI device numbers.

PipeWire sinks — real

What wpctl status / GNOME shows

  • Speaker + Headphones
  • soundcore R60i NC
  • HDMI / DisplayPort 1..3 (usually unused)

Laptop speakers and the wired jack share one sink; BT is separate.

Name patternMeaning
hw:CARD=…,DEV=n Raw hardware PCM #n (0 = analog, 3–5 often HDMI, 31 = deep buffer)
plughw: Same as hw: but ALSA converts sample rate/format for you
dmix: Software mixer so multiple apps can share the card
default / pipewire Follow the system default route (not a second speaker)
node.description (PipeWire) Friendly label used in Settings UI

3. How apps discover devices

1
Kernel + drivers register the card and Bluetooth adapter. Check with aplay -l (ALSA) or wpctl status (PipeWire).
2
PipeWire / WirePlumber create one Audio/Sink node per usable route, with properties media.class, node.name, node.description.
3
Apps query either:
  • PipeWire JSON dump → /usr/bin/pw-dump (what this app prefers), or
  • Pulse / GNOME APIs, or
  • ALSA via cpal → lots of aliases (what caused the old Settings list).
4
Filter monitors, null/dummy, HDMI (optional), and ALSA alias prefixes so the UI only shows devices a human would pick.

4. What the Prayer Times app does

Implemented in src-tauri/src/audio_output.rs. Listing and multi-speaker playback both prefer PipeWire. 

flowchart TD
  Settings[Settings: list_audio_output_devices]
  List[list_output_device_names]
  Dump["/usr/bin/pw-dump"]
  Parse[Parse JSON · Audio/Sink only]
  Filter[Drop HDMI + virtual + ALSA aliases]
  UI[UI: friendly names]
  Err[Clear error if none found]
  CPAL[Filtered cpal fallback]
  Play[Multi-speaker: pw-play --target per sink]

  Settings --> List
  List --> Dump
  Dump --> Parse --> Filter
  Filter -->|sinks found| UI
  Filter -->|empty / pw-dump failed| CPAL
  CPAL -->|usable names| UI
  CPAL -->|still empty| Err
  Filter --> Play

Key rules in code

  • Call /usr/bin/pw-dump and /usr/bin/pw-play with absolute paths (GUI / autostart often has a thin PATH).
  • Keep sinks where media.class == "Audio/Sink".
  • Show node.description (e.g. soundcore R60i NC), play to node.name.
  • Reject HDMI/DisplayPort and names starting with hw:, plughw:, dmix:, etc.
  • Never dump the raw ALSA alias list into Settings.

Multi-speaker note

“Play on all outputs” means all filtered PipeWire sinks, not every ALSA alias. On your laptop that is typically built-in Speaker+Headphones and Bluetooth — two streams, not seventeen.

Takeaway

Ubuntu detects hardware at the ALSA / Bluetooth layer, then PipeWire presents it as a small set of sinks. Apps that read ALSA see aliases; apps that read PipeWire see the real speakers. This app switched listing (and multi-speaker play) to PipeWire so Settings matches what you actually own.
